## Item 4: P11-S-01, HBB from its public recorded inputs

**What the audit had found.** The committed HBB set was built offline on 2026-11-03 from the Phase 6 live snapshot of 2026-11-02 (Reactome and Open Targets added live). Its manifest cites 44 bodies: 33 were public, 9 sat only in the local snapshot cache (`.cache/helix-raw`, not in the repository) and 2 (the Ensembl assembly and codon map) nowhere: the cache keeps at most 200 entries and had evicted them. `data/fixtures/hbb/index.json` points at the Phase 1 and 2 bodies (ClinVar .183, 74 submissions, URLs that once carried the redacted email parameter); rebuilt from them, HBB differed in 58 values. The other four sets were recorded through the fixture recorder, so their manifests cite the bytes on disk.

**Layout.** The package tests read the default HBB fixture set and expect its Phase 1 values (`VCV000015333.183` in `adapters.test.ts` and `hbb-plan.test.ts`), and `packages/` is not to be edited, so `data/fixtures/hbb/index.json` was left as it was. The HBB set's own inputs form a second set one level down, `data/fixtures/hbb/curated/`, with the layout and naming of the other sets (one folder per source, a `MANIFEST.tsv` each, `index.json`, file names from `fixtureFileName`), as the dynamic test inputs sit under `data/fixtures/dynamic/<symbol>/`. `build-gene.ts` gained `--fixture-set <set>` (with `--fixtures` only; pinned first). The recorder is `scripts/data-preparation/record-hbb-curated-inputs.ts`; its per-input report is `journal/results/hbb-curated-inputs-dh041.json`.

**Before copying.** Every cached HBB body was scanned for proprietary identifiers (the Q-H-LIC-1 guard), email addresses and key-like words. No email and no key or credential was found; the words matched were "secretory" and "secretion" (biology in the RCSB and Reactome bodies) and the field name "singletoken" of the ClinVar einfo body. Five bodies carried proprietary identifiers: the VEP body (4 removals), the ClinVar esummary (121), the ClinVar einfo (2), the HGNC record (`omim_id`, 1) and the UniProt entry (10 removals, and a MIM number left inside a comment's text, which the recorder's redaction does not reach). ## Interpretation

Hypothesis (3) holds: the dead line is gone and no displayed text changed; it frees 171 bytes of code but only 26 bytes over the wire. Hypothesis (4) holds for the values and fails for the hashes: anyone can now rebuild HBB's records from public inputs, and only provenance hashes of five sources differ, for two reasons that more requests cannot remove (redaction of the cited bodies, and Ensembl's unstable key order). Closing it fully needs a data change, left to the author: rebuild HBB through the fixture recorder so its manifest cites the public bytes (a new data version and a pin move), or accept it as stated.

## Failures

The first run of the recorder made the two authorised requests and then stopped, before writing anything, on the UniProt body that the recorder's redaction cannot clean; the two response bodies, held only in memory, were lost. The order was wrong: the redaction of the cached bodies should have run before any request. No request was repeated. The codon map response was recovered exactly by key-order search; the assembly response was not, and the Phase 1 body stands in for it, which changes nothing in the outcome since the response's sha256 already differed from the cited one.
