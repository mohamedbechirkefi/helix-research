## Method

1. **Wheel (S10).** A capture listener on the DNA canvas logged each wheel event's `deltaY` while safaridriver sent wheel actions in patterns (above). The app's handler (`DnaWorld.tsx` line 466, `zoomBy(exp(deltaY * 0.001))` per event) was read, not changed.
2. **Storage (S11).** A spy on `Storage.prototype.setItem` during a real toggle; then `setItem` and `getItem` in the same and in the next WebDriver call, inside one page script at 0, 100 and 1,000 ms, and from a page timer outside any WebDriver call, on the app and on `/THIRD-PARTY-NOTICES.txt` and `/release-manifest.json` at `127.0.0.1` and `localhost`. Control: a WKWebView with a non-persistent data store on the same WebKit build.
3. **Pin first** (invariant 2, helix-app 141d378): S10 `scales` counts the wheel events the canvas receives and checks sent equals delivered; the WebDriver page probes once whether localStorage persists between calls (`page.storagePersists`) and S11 records it. No behaviour change. Run before the fix in Chrome and Safari.
4. **Fix** (helix-app 3dca00b): `Mouse.wheel` in `e2e/webdriver.mjs` uses a fresh input-source id per call; S11 records its four localStorage-dependent checks as unsupported, not failed, when the probe finds storage does not persist (the app's write and read-back stay pinned by `test/sound.test.ts`). Then S10 and S11 in full, Safari and Chrome.

## Raw results

**Wheel delivery** (`probes/wheel.out`, `probes/wheel2.out`). Safari delivers the sent delta minus the delta it delivered last for the same input source, and drops an event of 0:

| Sent | Delivered |
|---|---|
| 80 x -40 (the suite's pattern), 33 ms or 200 ms apart | 40 events of -40, sum -1600; distance 6.0569 = 30 x exp(-1.600), the gate's stopping distance |
| -10, -20, -30, -40, -50 | -10, -10, -20, -20, -30 |
| 10 x -120 | +140, -260 alternating |
| 6 x -40 in one action sequence | 3 events |
| 6 x -40, actions released after each | -40, +40 pairs (the inverse scroll) |
| 6 x -40, a fresh input-source id each | 6 x -40 |
| 80 x -40 dispatched as WheelEvents inside the page | 80 events; the zoom reaches base pair (distance clamped at 2) |

**Storage** (`probes/storage.out`, `probes/storage3.out`). The app's toggle called `setItem('helix.sound', 'off')` on `window.localStorage` without an exception and `getItem` returned 'off' straight after; 300 ms later it was null, length 0. Without the app, on both origins: 'v' in the same script, null in the next WebDriver call; inside one page script, present at 0 ms and gone by 100 ms; a page-timer write is lost too. sessionStorage persists. Control: the WKWebView keeps the value after 1 s ("v,1").

**Pin, before the fix** (`pin/`): Chrome S10 `scales` exit 0. Safari S10 `scales` exit 1 with 4 failures, the first being the new pin: "the browser delivered 40 of 80 wheel events (deltaY sum -1600 of -3200)", then the gate's 3. Safari S11 (cues, off) exit 1, the gate's 4 failures; probe `{ sameScript: 'v', nextScript: null }`, persists false.

**After the fix** (`after/`): S10 exit 0 in Safari and in Chrome (Safari delivered 80 of 80, sum -3200; visited overview, codon, base pair). S11 exit 0 in Safari and in Chrome; Safari records 4 unsupported checks (the preference stored, the preference written, the reload keeps it, the first gesture after the reload), Chrome 0.

## Uncertainty

One machine, one Safari version; one run each for the pin and after runs. Not tested: a real mouse or trackpad in a non-automated Safari window (the step one notch gives, and storage outside automation). The control shows the same WebKit build keeps localStorage outside safaridriver; posting real OS scroll events would have meant driving the desktop, which was not done.

## Interpretation

Both failures are Safari's automation. The wheel fault is in WebDriver's simulated input (a visitor's wheel comes from macOS), and the harness now sends what it means to send; the storage fault is in the safaridriver session itself (it occurs with no app code involved), so those four checks cannot be run in Safari automation and are recorded as such. No app change is proposed (question 108 (b)). Known limitations 2.6 closes the Safari row as automation, app not at fault; the accessibility audit section 4.2 carries a pointer.
